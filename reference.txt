KOCHI TRANSIT — COMPLETE PROJECT TECHNICAL DOCUMENTATION
==============================================================

Document purpose
----------------
Master technical specification for a free-to-start Kochi Metro transit SaaS.

Product working name:
    Kochi Transit

Product statement:
    "Know where your train is, when it will arrive, and when you should leave."

IMPORTANT DATA ASSUMPTION
-------------------------
KMRL's current Open Data platform advertises GTFS Static and GTFS-Realtime
capabilities including vehicle positions, ETA predictions and service alerts.
Before production development, verify the exact public GTFS-RT endpoint,
authentication/access requirements, update frequency, available entities and
usage/licensing terms.

The existing kochimetro.keralam.co experience explicitly describes its train
locations as schedule-based rather than live. The project should therefore
differentiate itself through genuine realtime data where publicly accessible.

==============================================================
4. WHY THIS STACK
==============================================================

Angular:
    Strong fit for complex reactive UI and existing project expertise.

Signals:
    UI state, derived state, selected station/train, map state.

RxJS:
    HTTP streams, SSE, debouncing, search, realtime transformations.

MapLibre:
    Open-source map renderer with strong control over layers and animations.

CARTO:
    Can provide polished basemaps while MapLibre handles rendering.
    Keep a MapProvider abstraction so CARTO can later be replaced.

PostgreSQL + PostGIS:
    Best fit for geospatial queries such as nearest station, radius search,
    route geometry and geographic distance.

Redis/KV:
    Realtime vehicle state should not require database queries for every
    user request.

Fastify:
    Lightweight Node.js API layer and good fit with TypeScript.

Custom Metro graph:
    Kochi Metro's initial network is small enough that a dedicated graph is
    far simpler than deploying OpenTripPlanner immediately.

OpenTripPlanner:
    Add when the system becomes genuinely multimodal.

SSE:
    Realtime information mostly flows server -> browser, so SSE is simpler
    than WebSocket for the initial implementation.

==============================================================
6. DATA ARCHITECTURE
==============================================================

KMRL should be treated as an external provider.

Never make the Angular frontend depend directly on raw KMRL feed formats.

Architecture:

    KMRL raw data
        |
        v
    Ingestion layer
        |
        v
    Normalized internal model
        |
        +---- PostgreSQL/PostGIS
        |
        +---- Redis/KV for realtime

This makes it possible to replace the external feed later without rewriting
the entire frontend.

8. GTFS-REALTIME
==============================================================

Potential entities:

- Vehicle positions
- Trip updates
- Service alerts

Target normalized vehicle model:

{
    vehicleId,
    tripId,
    routeId,
    latitude,
    longitude,
    bearing,
    speed,
    currentStopId,
    nextStopId,
    status,
    sourceTimestamp,

IMPORTANT:
    sourceTimestamp and receivedAt are different.

A feed can be delayed even if the request succeeds.

==============================================================
12. REALTIME FRESHNESS
==============================================================

Define explicit states.

Example:

< 30 seconds:
    LIVE

30-90 seconds:
    RECENT

90 seconds-5 minutes:
    STALE

> 5 minutes:
    UNAVAILABLE

Make thresholds configurable.

Never display "LIVE" when the source data is stale.

UI example:

    LIVE
    Updated 8 sec ago

or:

    Data may be stale
    Last updated 2 min ago

==============================================================
13. REALTIME FAILURE STATES
==============================================================

If KMRL feed is unavailable:

    Do not crash the app.

Fallback:

    Last known realtime
        |
        v
    Static schedule

Display:

    "Live data temporarily unavailable.
     Showing scheduled times."

If Redis is unavailable:
    Realtime API becomes degraded but static data should continue.

If database is unavailable:
    Return proper health/degraded responses.

==============================================================
14. TRAIN POSITION INTERPOLATION
==============================================================

Realtime feeds may update every few seconds.

Example:

10:30:00:
    Position A

10:30:20:
    Position B

At 10:30:10:
    visually interpolate between A and B.

Keep two concepts:

    sourcePosition
    displayPosition

Never claim interpolated coordinates are measured GPS coordinates.

==============================================================
15. TRAIN LIFECYCLE
==============================================================

Train states:

    ACTIVE
      |
      v
    STALE
      |
      v
    EXPIRED
      |
      v
    REMOVED

Do not immediately remove a train when one update is missing.

This prevents map marker flickering.

16. TRAIN MATCHING
==============================================================

Prefer explicit identifiers:

    vehicleId

    routeId

    vehicle

    trip
      |
      v
    route

      v
    direction
      |

==============================================================
17. CLOCK AND TIMEZONE
==============================================================

Use:
    Asia/Kolkata

Prefer UTC for stored timestamps where practical.

Display:
    IST

GTFS times can exceed 24:00.

Example:

    25:10:00

means:

    01:10 next service day.

Do not naïvely parse GTFS times with JavaScript Date.

==============================================================
18. SERVICE DAY
==============================================================

A trip after midnight can belong to the previous service day.

The schedule engine must explicitly understand GTFS service dates.

==============================================================
19. STATION MODEL
==============================================================

Do not assume:

    station = one coordinate

Eventually model:

    Station
      |
      +-- Entrances
      +-- Platforms
      +-- Exits
      +-- Transfer paths
      +-- Accessibility information

Nearest station should eventually use entrance/walking distance rather than
only straight-line distance.

==============================================================
20. USER LOCATION
==============================================================

Use browser geolocation.

Possible states:

    Permission granted
    Permission denied
    Timeout
    Low accuracy
    GPS unavailable

Never require location.

Fallback:

    Search station manually.

Do not store precise location by default.

==============================================================
21. ROUTING ENGINE
==============================================================

MVP:
    Custom graph.

Model:

    Station = Node
    Track connection = Edge

Algorithm:

    Dijkstra
or:
    A*

For Kochi Metro's small graph, computational complexity is not the biggest
problem. Transit semantics are harder.

Later:
    OpenTripPlanner.

==============================================================
22. TRANSFER HANDLING
==============================================================

Do not assume:

    transfer time = 0

Use GTFS transfer data when available.

Otherwise use configurable station transfer defaults.

==============================================================
23. FARE ENGINE
==============================================================

Do not hardcode fares by number of stations.

Use imported fare data.

Flow:

    Origin
      |
      v
    Destination
      |
      v
    Fare lookup
      |
      v
    Fare result

Keep fare rules data-driven because prices can change.

==============================================================
24. ETA ENGINE
==============================================================

Priority:

1. Official TripUpdate ETA, if available.
2. Official vehicle position + route geometry.
3. Scheduled timetable as fallback.

Never promise exact arrival.

Use:

    Expected 08:37

or:

    ~08:37

not:

    Exactly 08:37

==============================================================
25. LEAVE-BY ENGINE
==============================================================

Signature feature.

Inputs:

    current location
    destination
    target arrival time
    walking time
    station
    available trains
    realtime ETA
    transfer time
    safety buffer

Concept:

    targetArrival
        -
    lastMileWalk
        -
    transitDuration
        -
    transfer
        -
    firstMileWalk
        -
    buffer
        =
    leaveBy

But actual train departure availability must be checked.

Example:

    Target: 09:00
    Destination walk: 5 min
    Metro: 17 min
    Transfer: 3 min
    Station walk: 6 min
    Buffer: 5 min

    Approximate leave time:
    08:24

Then validate against actual available departures.

==============================================================
26. DELAY IMPACT
==============================================================

Static:

    Scheduled arrival = 08:52

Realtime:

    Predicted arrival = 08:58

System:

    delay = +6 minutes

Then recompute the user's journey.

Example:

    Previous arrival: 08:52
    New arrival: 08:58
    Target: 09:00

    Result:
    Very small remaining buffer.

Never make unsupported certainty claims.

32. FAILURE HANDLING
==============================================================

KMRL feed down:
    Use cached/static schedule
    Show degraded state

Database down:
    Return health/degraded state

Redis down:
    Static API continues
    Realtime becomes degraded

Network down:
    PWA shell + cached station data
    Realtime unavailable

No GPS:
    Manual station search

Invalid coordinates:
    Reject or ignore the record

Missing vehicle:
    Mark stale before removal

==============================================================
33. EDGE CASES
==============================================================

GTFS:
    - Invalid references
    - Missing stations
    - Invalid shapes
    - Duplicate trips
    - Times beyond 24:00
    - Service-day boundaries
    - Feed version changes

Realtime:
    - Missing vehicle ID
    - Missing trip ID
    - Missing coordinates
    - Duplicate vehicles
    - Stale timestamp
    - Future timestamp
    - Invalid latitude
    - Invalid longitude
    - Train disappears
    - Feed outage
    - Partial feed update
    - Out-of-order messages

Journey:
    - Origin is station
    - Origin is arbitrary GPS point
    - Destination is station
    - Destination is arbitrary GPS point
    - No route
    - Last train
    - First train
    - Target arrival already impossible
    - Very tight buffer
    - Station transfer
    - User misses train

UI:
    - Offline
    - Slow network
    - Empty search
    - No trains
    - Stale data
    - Location denied
    - Reduced motion
    - Small screen

==============================================================
34. TIME EDGE CASES
==============================================================

Handle:

    Midnight
    24+ hour GTFS times
    Daylight-saving assumptions are not relevant to IST
    Device clock incorrect
    Server clock incorrect
    KMRL timestamp delayed
    Service date vs calendar date

Prefer server/provider timestamps for transit logic.

==============================================================
35. MAP EDGE CASES
==============================================================

- GPS outside Kochi
- GPS near multiple stations
- Train slightly outside route geometry
- Duplicate markers
- Marker flicker
- Missing route geometry
- Map tile provider outage
- Map tile quota exceeded
- Low-end phone performance
- Reduced motion

Use MapLibre layers rather than hundreds of DOM markers.
